# Report Writing Agent — Presentation Script

> **Presenter Notes:** This script covers the Report Writing Agent in the SC4063 pipeline. Each section maps to slides in `report_writing_agent_slides.html`. Timing annotations are for a ~10-minute focused segment.

---

## Slide 1 — Title (20 seconds)

This section focuses on the **Report Writing Agent** — the final synthesis component of our pipeline. After the four forensic agents have completed their analysis, the report writer takes all of their structured findings and produces a professional incident response report — fully autonomously.

The report writer is not just a formatting step. It's an LLM-driven agent that must reason across multiple days of findings, deduplicate IOCs, map everything to MITRE ATT&CK, and produce a coherent narrative — all while being constrained to never fabricate evidence.

---

## Slide 2 — Architecture: Where the Report Writer Fits (1 minute)

The report writer sits at the end of the pipeline, after all four forensic agents and MITRE enrichment have completed.

Here's the flow: The **supervisor** routes agents in a fixed order — Initial Access, Lateral Movement, Exfiltration, Payload. After all four complete, the supervisor routes to **MITRE ATT&CK enrichment**, which maps findings to 835 technique definitions. Finally, everything flows to the **Report Writing Agent**.

The report writer receives seven key inputs from the shared `PipelineState`:
1. **Target day** — which day is being reported
2. **Initial Access findings** — patient zero, attacker IP, brute-force counts
3. **Lateral Movement findings** — compromised hosts, movement paths, techniques
4. **Exfiltration findings** — detected flag, destinations, protocols, volumes
5. **Payload findings** — deployment method, suspicious files, hashes
6. **Attack context** — accumulated intelligence across all prior days
7. **MITRE enrichment** — matched techniques and candidate threat groups

All of these are serialised as JSON and passed to the LLM in a single structured prompt. The attack context is especially important for multi-day reports — it carries forward facts like the patient zero IP and compromised host list from earlier days.

---

## Slide 3 — Two Modes: Single-Day vs. Multi-Day (1 minute)

The report writer operates in two modes.

**Single-day mode** uses the `report_writing_node()` function. It takes one day's findings from PipelineState, serialises everything as JSON, passes it to GPT-4o-mini with our system prompt, and saves the result as both Markdown and PDF. The output file is named `incident_report_YYYY-MM-DD.md`.

**Multi-day mode** uses the `write_combined_report()` function. This is what runs at the end of the full 9-day pipeline. It receives a list of all per-day results and does three critical things before calling the LLM:

First, it **deduplicates IOCs** — the same attacker IP might appear in findings for Day 1, Day 3, and Day 7. We deduplicate by `(ioc_type, value)` tuple so each IOC appears exactly once.

Second, it **deduplicates MITRE techniques** — technique T1021.001 (Remote Desktop Protocol) might be matched on multiple days. We deduplicate by `attack_id`.

Third, it **deduplicates threat groups** — same group might match on multiple days. We deduplicate by `group_id` and take the top 10 by technique overlap count.

The consolidated prompt then includes per-day sections separated by visual dividers, plus the deduplicated IOC list, MITRE techniques, and threat groups at the end. The output is saved as `combined_incident_report.md` and `combined_incident_report.pdf`.

## Slide 4 — Report Structure: 8 Mandatory Sections (1 minute)

The system prompt mandates exactly 8 sections in a specific order. The LLM is constrained to follow this structure.

**Section 1: Title/Cover Page** — Incident report header with date range and case identifier.

**Section 2: Table of Contents** — Generated by the LLM to match the actual sections.

**Section 3: Executive Summary** — Written for a C-suite audience. Must cover root cause, business impact, and priority recommendations. This is where the LLM synthesises the "so what" from all the technical findings.

**Section 4: Detailed Findings** — This is the largest section. It's organised by attack phase: Initial Access, Lateral Movement and Discovery, Exfiltration, and Payload. Each finding is mapped to MITRE ATT&CK technique IDs and names. Candidate threat groups are assessed with likelihood based on technique overlap.

**Section 5: Conclusion and Recommendations** — Prioritised as High, Medium, and Low. Must be actionable — not generic security advice but specific to what was found.

**Section 6: Appendix — Timeline** — Chronological reconstruction of events across all analysed days.

**Section 7: Appendix — Technical Details** — Extended evidence: packet traces, IOC details, 5-tuples.

**Section 8: Evidence Gaps** — This is critical. The LLM must explicitly state what the pipeline could NOT determine — missing data, scope limitations, unresolved questions. This prevents silent gaps from being overlooked.

Additionally, if provenance tracking is enabled, a **9th section** — the Evidence Provenance Appendix — is auto-appended. It lists exactly which PCAP and Zeek files each agent accessed on each day.

## Slide 5 — LLM Configuration and Anti-Hallucination (1.5 minutes)

The report writer uses **Azure OpenAI GPT-4o-mini** with very specific configuration choices.

**Temperature: 0.1** — Near-deterministic. We sacrifice prose fluency for factual consistency. Forensic reports need reproducibility — running the same data twice should produce substantially similar reports.

**Max tokens: 16,000** — This gives the LLM enough budget for a comprehensive multi-day report with all 8 sections, MITRE mappings, timeline, and appendices.

Now, the anti-hallucination rules. There are four explicit rules in the system prompt:

**Rule 1: Evidence references required.** "Every significant claim must include supporting evidence references." The LLM cannot make assertions without citing data.

**Rule 2: Concrete references preferred.** "Prefer concrete references: 5-tuples, host/user identifiers, timestamps, log sources." Not vague statements — real network data.

**Rule 3: Insufficient evidence fallback.** "If evidence is missing, write 'Insufficient evidence' rather than guessing." This is the most important rule. It gives the LLM an explicit escape hatch that doesn't require fabrication.

**Rule 4: Fabrication blacklist.** "Never fabricate packet IDs, hashes, users, hosts, ATT&CK IDs, or timestamps." A specific list of things the LLM is forbidden from inventing.

These rules are **proactive** — enforced via the system prompt and low temperature, not via post-generation validation. The philosophy is: constrain the generation itself rather than trying to catch errors after.

## Slide 6 — PDF Generation Pipeline (1 minute)

The Markdown report is converted to a professional PDF using **ReportLab Platypus**.

The `_save_pdf()` function implements a custom Markdown-to-PDF renderer. Here's what it handles:

**Page setup:** A4 size, 2 cm margins on all sides.

**Typography:**
- H1 headings: 18pt with a horizontal rule below
- H2 headings: 14pt
- H3 headings: 12pt
- Body text: 10pt with 14pt line height
- Code blocks: 8pt Courier font, indented
- Bullet points: Indented with bullet markers

**Markdown parsing:** The renderer processes each line and handles:
- Heading levels (`#`, `##`, `###`)
- Bold (`**text**`), italic (`*text*`), and inline code (`` `code` ``)
- Bullet lists (`- `, `* `, `+ `)
- Code blocks (triple backtick fenced)
- Tables (rendered in monospace font)
- Horizontal rules (`---`, `===`)

**Security:** All text is XML-escaped before passing to ReportLab to prevent injection — `&`, `<`, `>` are all escaped.

**Table handling:** The system prompt enforces a critical rule — table cells must be **single-line**. No line breaks, no bullet points inside cells. If multiple items need listing, they must be semicolon-separated. This prevents the PDF renderer from choking on multi-line cells.

The markdown formatting rules in the system prompt also say: "For detailed evidence that doesn't fit in a table, use a bullet list BELOW the table under a 'Supporting Evidence' sub-heading." This guides the LLM toward PDF-friendly output.

## Slide 7 — Provenance Tracking (45 seconds)

Provenance tracking provides a complete audit trail of the report's evidence basis.

The `ProvenanceLog` class records four categories:
1. **PCAPs analysed** — per-day PCAP file names, paths, and sizes
2. **Zeek log files used** — per-day list of Zeek dataset filenames
3. **Per-agent source files** — which agent accessed which files on which day
4. **Days analysed** — chronological list of all days processed

When enabled via `--track-provenance`, this data is formatted as a Markdown appendix with three tables and auto-appended to the report content before PDF generation.

This is critical for auditability. A reviewer can look at the provenance appendix and understand: "The lateral movement findings for Day 3 were based on `zeek.smb_files.ndjson` and `zeek.rdp.ndjson` — not on PCAP data." If an agent didn't access a particular data source, that's visible, and the reviewer can assess whether findings might have gaps.

## Slide 8 — Key Challenges for the Report Writer (1 minute)

**Challenge 1: Context window pressure.** A 9-day combined report can have massive input — all agent findings, IOCs, MITRE data, attack context across 9 days. With GPT-4o-mini's context window, this requires careful serialisation and the 16K output token budget constrains report length.

**Challenge 2: Table formatting compliance.** LLMs naturally want to put multi-line content in table cells, but ReportLab's PDF renderer cannot handle this. The system prompt includes explicit WRONG/RIGHT examples to prevent this, but it's not guaranteed — the enforcement is best-effort via prompt engineering.

**Challenge 3: Evidence attribution accuracy.** The LLM must correctly attribute findings to the right day, the right IP, the right MITRE technique. With 9 days of similar-looking data, cross-contamination between days is a risk. The per-day sections with visual separators help, but this remains a challenge.

**Challenge 4: No post-generation validation.** Unlike the exfiltration agent which has a grounding check, the report writer has no automated fact-checking of its output. If the LLM cites a timestamp that doesn't exist in the input, we won't catch it automatically. The mitigation is the low temperature and strict prompting — but it's a known limitation.

## Slide 9 — Cost and Efficiency (45 seconds)

The report writer is one of the most cost-efficient components in the pipeline.

**LLM calls:** Just 1 call for a single-day report, 1 call for the combined multi-day report. Compare this to the Initial Access agent which may make 30+ tool calls.

**Estimated cost:** At GPT-4o-mini pricing (~$0.15/M input tokens, ~$0.60/M output tokens), a combined report costs approximately $0.10 to $0.20 per generation. The input is large (all findings serialised), but the model is cost-effective.

**Time:** Report generation takes approximately 2 minutes — almost entirely LLM inference time. PDF rendering is near-instant.

**Trade-off:** We use GPT-4o-mini instead of GPT-4o for cost efficiency. For structured forensic reporting where the data is already pre-analysed by specialist agents, mini provides sufficient quality. The report writer doesn't need to reason about raw network data — it synthesises pre-structured findings. This makes it an ideal use case for the smaller model.

## Slide 10 — Summary (30 seconds)

To summarise the Report Writing Agent:

- It's a **single-call LLM agent** that synthesises all forensic findings into a structured incident report
- It supports both **single-day** and **multi-day** modes with IOC/MITRE deduplication
- It produces **8 mandatory sections** following a forensic report standard
- Anti-hallucination relies on **4 explicit rules** in the system prompt plus **temperature 0.1**
- Output is both **Markdown and PDF** via a custom ReportLab renderer
- **Provenance tracking** provides a full audit trail of evidence sources
- Cost is minimal — approximately **$0.10–$0.20 per report**, generated in ~2 minutes

The report writer demonstrates that with proper constraints, structured inputs, and low temperature, an LLM can produce auditable forensic reports without fabricating evidence.
